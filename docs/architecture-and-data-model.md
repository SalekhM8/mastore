# Sync: Architecture and Data Model

Status: v1 design, 9 September 2026. This is the document the first migrations are written from. Change it before changing the schema, not after.

Companion documents: `security-and-compliance.md`, `reliability-and-operations.md`, `engineering-standards.md`.

## 1. The one idea

The seller's catalog is the source of truth. Every marketplace is a projection of it. Nothing writes stock except the stock ledger. A marketplace sale is an inbound ledger event; every ledger event fans out as outbound push jobs to every other connected channel. If that loop is correct, fast and visible, the product works. Everything else is UI.

Three consequences that shape the schema:

1. **Append-only ledger, derived projection.** Current quantity is never edited. It is computed from events and cached in a projection row that is updated in the same transaction as the event.
2. **Outbox, not fire-and-forget.** The push jobs that a ledger event causes are inserted in the same transaction as the event. A crash between "record the sale" and "tell eBay" cannot lose the push.
3. **Connectors are dumb.** A connector translates between one marketplace's API and our normalised types. It never touches the ledger. It emits normalised inbound events and executes normalised push jobs.

## 2. Runtime topology

```
Seller browser ──► Next.js (Vercel) ──► Supabase Postgres (RLS, as the user)
                                    └──► Supabase Storage (photos)

Marketplace ──webhook──► /api/webhooks/{channel} (Vercel) ──verify, store, ack──► Inngest event
                                                                                   │
Inngest ──► job functions (Vercel, service role, workspace-scoped) ──► Postgres (ledger, jobs)
        └──► connector calls ──► Marketplace APIs
        └──► cron: reconcile polls, digests, secret rotation reminders

Stripe ──webhook──► /api/webhooks/stripe ──► stripe_events (idempotent) ──► workspace billing state
```

- **Web tier** runs as the signed-in user. Supabase Auth session, RLS enforces tenancy. Server Actions and Route Handlers only.
- **Job tier** is Inngest functions deployed in the same Next.js app. They use the service role key and therefore bypass RLS, so every query in the job tier goes through a repository that requires a `WorkspaceId` argument. No repository function accepts "all workspaces".
- **Webhook ingress** does exactly four things: verify signature, insert into `channel_events` (dedupe on external event id), emit an Inngest event, return 200. Target under 200 ms. All parsing happens in the job tier.
- **No long-lived worker in v1.** Inngest gives retries, throttling per key, concurrency limits, cron, and step-level durability, which is the "dedicated worker" from the blueprint without running one. Revisit if a connector needs a persistent connection.

## 3. Identity and tenancy

| Table | Purpose |
|---|---|
| `auth.users` | Supabase managed. Never referenced by business tables except through `workspace_members`. |
| `workspaces` | One per seller business. Holds billing state, settings, feature flags. |
| `workspace_members` | `(workspace_id, user_id, role)`. Role is `owner` or `member`. v1 UI only creates owners; the table exists so teams are a UI change later. |

RLS pattern for every tenant table:

```sql
create policy tenant_isolation on public.<table>
  for all to authenticated
  using ((select private.is_workspace_member(workspace_id)))
  with check ((select private.is_workspace_member(workspace_id)));
```

`private.is_workspace_member` is a `security definer` function in a non-exposed schema that checks `workspace_members` for `(select auth.uid())`. It is wrapped in `select` so Postgres evaluates it once per query, not once per row. Every tenant table has an index that starts with `workspace_id`.

Global tables (`fee_schedules`, `channel_taxonomies`) are readable by `authenticated`, writable only by `service_role`. Append-only tables (`ledger_events`) revoke `update` and `delete` from every role including `service_role`, enforced with a trigger that raises.

## 4. Identifiers, money, time

- **Primary keys** are UUID v7 (time-ordered, so inserts do not fragment indexes) generated by a SQL function `private.uuid_v7()` in the first migration. No extension dependency.
- **External ids** from marketplaces are stored as `text`, never parsed into numbers, always alongside the `channel_account_id` they belong to.
- **Money** is integer minor units (`bigint`, pence) with a `currency` column (`char(3)`, always `GBP` in v1). No `numeric`, no floats. Column names end in `_minor`.
- **Time** is `timestamptz` everywhere. `occurred_at` is when the marketplace says it happened, `recorded_at` is when we wrote it. Both are kept because they disagree during backfills.
- **Quantities** are `integer`. Negative on-hand is allowed in the projection because it is how an oversell is detected, not prevented.

## 6. Channels

One row per connected marketplace account. A seller can have two eBay accounts; each is its own row.

|---|---|---|

A separate view `channel_accounts_public` excludes `credentials_ciphertext` and is what the web tier reads.

### `channel_listings`
The link between a SKU and its representation on one channel account. This is the most important join table in the system.

| Column | Type | Notes |
|---|---|---|

| external_ids | jsonb | Secondary ids: eBay offer id and inventory item key, TikTok sku id, Amazon ASIN |
| listing_model | text null | eBay only: `inventory` or `trading`. Decides which API updates quantity |
| status | text | `draft`, `pending`, `active`, `ended`, `error`, `unmanaged` |

| price_minor | bigint null | Channel-specific price. Null means use product price times channel multiplier |
| desired_quantity | integer | What the ledger says this channel should show |
| pushed_quantity | integer null | What we last successfully pushed |
| pushed_at | timestamptz null | |
| remote_quantity | integer null | What the last reconcile poll saw |
| remote_checked_at | timestamptz null | |
| applied_ledger_seq | bigint | Highest ledger sequence applied to this listing. The ordering guard |
| last_error | jsonb null | Normalised error for the sync page |
| channel_payload | jsonb | Channel-specific listing fields: eBay item specifics, TikTok attributes, category ids |

Drift is `desired_quantity <> remote_quantity` after a reconcile. That row turns amber on the sync page.

### `channel_category_mappings` and `channel_taxonomies`
`channel_taxonomies` caches each marketplace's category tree and aspects: `(channel, marketplace, version, fetched_at, payload jsonb)`, global. `channel_category_mappings` is per workspace: `(workspace_id, channel, category_path, external_category_id, aspect_defaults jsonb)`. A product's `category_path` resolves to a channel category through it. Populated from the taxonomy at first publish and remembered.

## 7. The stock ledger

### `ledger_events`
Append-only. The truth.

| Column | Type | Notes |
|---|---|---|
| seq | bigint identity | Global monotonic sequence. The ordering primitive |
| id, workspace_id, sku_id | uuid | |
| kind | text | `sale`, `cancellation`, `return`, `restock`, `manual_adjust`, `import_baseline`, `correction` |
| quantity_delta | integer | Negative for sale, positive for restock. Never zero |
| source_channel_account_id | uuid null | Which channel caused it. Null for manual |
| order_line_id | uuid null | For sale, cancellation, return |
| idempotency_key | text | Unique per workspace. Format in section 10 |
| occurred_at, recorded_at | timestamptz | |
| actor | text | `system:ebay_webhook`, `user:{uuid}`, `system:reconcile` |
| metadata | jsonb | Anything useful for audit |

No `update` or `delete` for any role. A mistake is fixed by a `correction` event that references the bad one in metadata.

### `sku_stock`
The projection. One row per SKU.

`(sku_id pk, workspace_id, on_hand integer, last_event_seq bigint, updated_at)`

### `apply_ledger_event(...)`
A single Postgres function is the only write path into both tables. It runs with definer rights, because insert on `ledger_events`, `sku_stock` and `push_jobs` is revoked from the web tier; RLS therefore does not apply inside it, so its first statement checks that a signed-in caller is a member of `p_workspace_id` (the service role, for which `auth.uid()` is null, is trusted to pass the right one). It runs in one transaction:

1. `select ... for update` the `sku_stock` row. This serialises all events for one SKU and is what makes ordering per SKU trivial.
2. Insert into `ledger_events`. If `idempotency_key` conflicts, return the existing event and stop. This is the exactly-once guarantee under at-least-once webhook delivery.
3. Update `sku_stock.on_hand` and `last_event_seq`.
4. For every `channel_listings` row for this SKU that is `managed`, `active` or `pending`, with `sync_enabled` on its account, and that is not the source of the event: set `desired_quantity`, and upsert a `push_jobs` row (section 9). This is the outbox.
5. If the SKU is `unique` and `on_hand` is now below zero, or if `on_hand` went below zero at all, insert an `incidents` row of kind `oversell` with the competing listings. The event is still recorded. The marketplace already sold it; our job is to tell the seller in seconds, not to pretend it did not happen.
6. Return the new `on_hand` and the list of created job ids.

The job tier then emits one Inngest event per push job. If the process dies after commit and before emit, a cron every minute picks up `push_jobs` in `queued` older than 60 seconds and emits them. The outbox is never lost.

## 8. Orders

### `orders`
`(id, workspace_id, channel_account_id, external_order_id, status, currency, subtotal_minor, postage_charged_minor, total_minor, fees_minor null, buyer_display text null, ship_to_country char(2) null, ship_to_postcode_area text null, placed_at, updated_at, raw_ref uuid null)`

Unique on `(channel_account_id, external_order_id)`. Status is our normalised enum: `created`, `paid`, `shipped`, `delivered`, `cancelled`, `returned`, `partially_refunded`.

Deliberately absent in v1: buyer full name, email, phone, street address. We do not need them to sync stock or compute margin, and holding them puts us in Amazon's restricted role and section 2 of their Data Protection Policy. The `raw_ref` points at the `channel_events` row so nothing is lost if we need it later; that row is retained 90 days.

### `order_lines`
`(id, workspace_id, order_id, external_line_id, channel_listing_id null, sku_id null, external_listing_id, title_snapshot, quantity, unit_price_minor, line_fees_minor null, status)`

Unique on `(order_id, external_line_id)`. `sku_id` is null when the sold listing is not attached to a SKU; the sale is recorded, shown as unmatched on the sync page, and produces no ledger event until the seller attaches it.

## 9. Inbound and outbound

### `channel_events` (inbound)
Every webhook and every poll result lands here before anything else happens.

`(id, channel, channel_account_id null, external_event_id text, topic, received_at, signature_valid boolean, payload jsonb, status, processed_at, error jsonb, workspace_id null)`

Unique on `(channel, external_event_id)`. For channels without a stable event id (polls), the id is a hash of the resource id and its modified timestamp. Status is `received`, `processed`, `ignored`, `failed`. Retention 90 days, then purged by cron. This table is also the replay log: any event can be reprocessed by id.

### `push_jobs` (outbound)
The outbox and the seller's visible queue.

| Column | Type | Notes |
|---|---|---|
| id, workspace_id, channel_account_id, channel_listing_id | uuid | |
| kind | text | `stock`, `price`, `listing_create`, `listing_update`, `delist`, `relist` |
| desired | jsonb | `{quantity: 0}` or `{price_minor: 2499}` or the full listing payload |
| ledger_seq | bigint | The event that caused it. Applied only if greater than `channel_listings.applied_ledger_seq` |
| priority | smallint | 0 is a sale-driven stock or delist push. 5 is price. 9 is bulk import. Throttle keys drain in priority order |
| status | text | `queued`, `running`, `succeeded`, `failed`, `superseded`, `dead` |
| attempts | integer | |
| next_attempt_at | timestamptz | |
| last_error | jsonb null | Normalised: `{code, retryable, message_for_seller}` |
| created_at, started_at, finished_at | timestamptz | |

Coalescing: a partial unique index on `(channel_listing_id, kind) where status = 'queued'`. A newer `stock` job for the same listing updates the queued row's `desired` and `ledger_seq` instead of adding a second row. A listing that sold three times in ten seconds produces one push with the final quantity.

### Inngest functions
- `push/{channel}`: triggered by `push.requested {job_id}`. Concurrency key `channel_account_id`, limit 1, so pushes to one account are serial and ordered. Throttle key `channel_account_id` set per channel from the rate limit table in the reliability doc. Steps: load job, check `ledger_seq` guard, call connector, record result, update `channel_listings`.
- `inbound/{channel}`: triggered by `inbound.received {event_id}`. Parses the payload with the connector, calls `apply_ledger_event` or upserts orders, marks the event processed.
- `reconcile/{channel}`: cron per channel. Pulls orders since last watermark and listing quantities, compares to `channel_listings`, records drift, heals when safe.
- `outbox/sweep`: every minute, re-emits queued jobs older than 60 seconds.
- `billing/*`, `analyst/weekly`, `secrets/rotation-reminders`: cron.

## 10. Idempotency keys

One format, built by a single function, used everywhere:

```
{channel}:{external_account_id}:{resource}:{resource_id}:{action}[:{qualifier}]
```

Examples:
- `ebay:seller123:orderline:12-34567-89012:sale`
- `tiktok:7495…:orderline:5768…:cancel`
- `user:{uuid}:sku:{sku_id}:restock:{client_generated_uuid}` for manual adjustments from the UI, where the client generates the uuid so a double-clicked button is one event.
- `import:ebay:seller123:listing:1234567:baseline` for the initial quantity import.

A duplicate key is not an error. It returns the original event and the caller carries on.

## 11. Money and margin

### `fee_schedules` (global)
`(id, channel, marketplace, account_type null, effective_from date, effective_to date null, version, rules jsonb, source_url, notes)`

`rules` is a small declarative structure the margin engine interprets: percentage of item, percentage of item plus postage, per-order fixed, regulatory percentage, VAT on fees flag, category overrides. The schedule in force for a sale is the row where `effective_from <= placed_at::date < coalesce(effective_to, 'infinity')`. Changing a fee is inserting a new row with a new `effective_from`, never editing.

### `sale_costings`
`(order_line_id pk, workspace_id, fee_schedule_id, gross_minor, fees_minor, postage_cost_minor, cost_minor null, net_minor null, margin_bps null, computed_at, inputs jsonb)`

A projection. Recomputable at any time from the order line, the SKU cost, and the fee schedule. `net_minor` is null when `cost_minor` is null, and the UI shows "payout after fees" instead of "profit". That is the graceful degradation for sellers who have not entered costs yet.

## 12. Operations tables

- `incidents`: `(id, workspace_id, kind, severity, sku_id null, channel_account_id null, channel_listing_id null, details jsonb, status, created_at, acknowledged_at, resolved_at)`. Kinds: `oversell`, `push_dead`, `auth_revoked`, `drift`, `webhook_signature_failed`. Drives alerts and the sync page banner.
- `activity_log`: the seller-facing feed on the sync page. `(id, workspace_id, channel_account_id null, sku_id null, level, message, context jsonb, created_at)`. Written by the job tier in plain language: "eBay: Nike Air Max UK 9 set to 0 after a sale on Depop, 1.8 seconds."
- `deletion_requests`: `(id, channel, external_user_id, received_at, workspace_ids uuid[], completed_at, evidence jsonb)`. eBay's account deletion notifications land here and a job deletes everything for that external user, then records what it deleted.
- `stripe_events`: `(id text pk, type, payload jsonb, received_at, processed_at)`. Stripe's own event id is the primary key, which is the idempotency.
- `ai_permissions`: `(workspace_id, capability, level, bounds jsonb)`. Levels `suggest`, `auto_bounded`, `auto`. v1 UI only writes `suggest`. Present from day one so the model's permission is data, not code.
- `analyst_digests`: `(id, workspace_id, period_start, period_end, findings jsonb, summary text, model text, sent_at, opened_at)`.
- `audit_events`: `(id, workspace_id, actor_user_id null, action, object_type, object_id, before_hash, after_hash, ip, user_agent, created_at)`. Every mutation through a Server Action writes one. Retained 12 months. Defined in the security document.
- `system_notices`: `(id, scope, channel null, channel_account_id null, severity, message, link, starts_at, ends_at)`. Drives banners on the sync page, which is the status page in v1. Defined in the reliability document.
- `order_buyer_details`: `(order_id pk, workspace_id, name, address jsonb, email, phone, purge_after)`. Exists in the schema so PII never lands in `orders`, but nothing writes to it in v1. When a channel requires buyer details for a feature, the security document's section 2 controls come into force first.

## 13. The connector contract

Every channel implements this and nothing more. Normalised types live in `src/domain/channels/types.ts`; the interface in `src/connectors/contract.ts`.

```ts
interface ChannelConnector {
  readonly channel: Channel;
  // Auth
  buildAuthorizeUrl(input: { workspaceId; state; redirectUri }): Promise<URL> | null; // null for paste-token channels
  exchangeAuthCode(input): Promise<CredentialBundle>;
  refreshCredentials(bundle): Promise<CredentialBundle>;
  healthCheck(account): Promise<HealthReport>;
  // Catalog import
  listRemoteListings(account, cursor?): Promise<Page<RemoteListing>>;
  // Outbound
  pushStock(account, listing, quantity): Promise<PushResult>;
  pushPrice(account, listing, priceMinor): Promise<PushResult>;
  createListing(account, product, sku, channelPayload): Promise<PushResult<RemoteListingRef>>;
  updateListing(account, listing, changes): Promise<PushResult>;
  delist(account, listing): Promise<PushResult>;
  // Inbound
  verifyWebhook(rawRequest): Promise<{ valid: boolean; externalEventId: string; topic: string }>;
  parseInbound(event: ChannelEventRow): Promise<NormalisedInbound[]>; // sales, cancellations, listing changes
  pullOrders(account, since): Promise<Page<NormalisedOrder>>;
  pullListingQuantities(account, listings): Promise<Map<listingId, number>>; // for reconcile
  // Capabilities
  capabilities(): { multiQuantity: boolean; webhooks: boolean; createListings: boolean; priceUpdates: boolean };
}
```

`PushResult` is a discriminated union: `ok`, `retryable {after?}`, `terminal {reason}`, `auth_revoked`, `rate_limited {retryAfter}`. The job runner maps these to Inngest retry behaviour. A connector never throws for an expected API failure.

`capabilities()` is how the rest of the system knows Vinted cannot do quantity greater than one and OnBuy has no webhooks, without `if (channel === 'vinted')` scattered through the code.

## 14. Four flows, end to end

**A sale on eBay for a unique item also listed on Depop and Vinted.**
eBay posts `ORDER_CONFIRMATION` to `/api/webhooks/ebay`. Signature verified against the cached eBay public key. Row inserted into `channel_events`, Inngest event emitted, 200 returned in about 80 ms. `inbound/ebay` runs: calls `getOrder`, upserts `orders` and `order_lines`, resolves the line's `external_listing_id` to a `channel_listings` row and its `sku_id`, calls `apply_ledger_event` with a `sale` of minus one. The function locks `sku_stock`, records the event, sets `on_hand` to zero, and inserts two `push_jobs` of kind `delist`, priority 0, one each for the Depop and Vinted listings. Two Inngest events fire. `push/depop` and `push/vinted` run concurrently, each with its own throttle. Both succeed. `channel_listings` for those two go to `ended`, `activity_log` gets three lines, and the sync page shows the sale and both delists with timings. Typical wall clock from eBay's POST to Vinted's delist acknowledged: two to six seconds, dominated by the marketplaces.

**The seller types a new quantity of 12 for a stocked SKU.**
Server Action validates with zod, computes the delta against `sku_stock.on_hand`, calls `apply_ledger_event` with `manual_adjust`, actor `user:{id}`, and an idempotency key containing a client-generated uuid. Push jobs of kind `stock` are created for every active listing of that SKU on every channel. Same path as a sale. There is no special case for manual edits.

**Publishing an existing product to TikTok for the first time.**
The seller picks the channel. UI resolves category via `channel_category_mappings`, asks for any missing TikTok attributes, and inserts a `channel_listings` row in `draft` plus a `push_jobs` row of kind `listing_create`, priority 5. `push/tiktok` calls `createListing`, stores the returned ids in `external_listing_id` and `external_ids`, sets status `pending` until TikTok's `PRODUCT_STATUS_CHANGE` webhook says it is live, then `active`. From that moment it participates in stock fan-out.

**Importing 800 existing eBay listings at sign-up.**
`import/ebay` pages through `listRemoteListings` in Inngest steps of 100. For each remote listing it upserts a `products` and `skus` row (matching on the seller's SKU, then on title plus photo hash to catch the same item already imported from another channel), inserts a `channel_listings` row with `managed = false`, and records an `import_baseline` ledger event with the remote quantity. Nothing is pushed anywhere. The seller then reviews: confirm unique versus stocked where ambiguous, attach duplicates, paste cost prices. Flipping `sync_enabled` on the account and `managed` on the listings is what starts the fan-out. Import never causes an outbound call.

## 15. Indexes that must exist on day one

- Every tenant table: `(workspace_id, ...)` leading.
- `ledger_events (sku_id, seq)`, unique `(workspace_id, idempotency_key)`.
- `channel_listings` unique `(channel_account_id, sku_id)`, unique `(channel_account_id, external_listing_id)`, `(sku_id)`, partial `(workspace_id) where desired_quantity is distinct from remote_quantity`.
- `push_jobs (status, next_attempt_at) where status in ('queued','failed')`, `(channel_account_id, status)`, partial unique `(channel_listing_id, kind) where status = 'queued'`.
- `channel_events` unique `(channel, external_event_id)`, `(status, received_at)`.
- `orders` unique `(channel_account_id, external_order_id)`, `(workspace_id, placed_at desc)`.
- `order_lines` unique `(order_id, external_line_id)`, `(sku_id)`.
- Every foreign key column.

## 16. What is deliberately not in v1

- Buyer PII beyond country and postcode area.
- Multi-currency. `currency` columns exist so it is a data change, not a schema change.
- Team roles beyond owner. The table exists; the UI does not.
- Shipping labels, carriers, tracking push. Orders are read for stock and margin only.
- A separate read model or cache. Postgres with the right indexes serves 1,000 sellers comfortably; see the reliability doc for the numbers.
- Partitioning of `ledger_events` or `channel_events`. Planned for when either passes 50 million rows.

## 17. Decisions log

| Decision | Chosen | Rejected | Why |
|---|---|---|---|
| Queue | Inngest with Postgres `push_jobs` as the visible outbox | pg-boss on a worker, BullMQ on Redis | Durability, per-key throttling and cron without a server to run; Postgres row is what the seller sees |
| Ledger write path | One Postgres function, row lock per SKU | Application-level transaction with optimistic concurrency | Ordering and idempotency in one place, testable with plain SQL |
| Ids | UUID v7 via SQL function | bigint identity, UUID v4 | Exposed in URLs and webhooks, time-ordered for index locality, no extension |
